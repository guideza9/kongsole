01

tool จัดการสิ่งที่กั้นตัวมันเอง

Admin API ถูกครอบด้วย Kong เอง — loopback service ชี้ไป http://127.0.0.1:8001 + route + basic-auth plugin แปลว่า เส้นทางเข้า Admin API ทั้งเส้นเป็น Kong entity ที่ tool จะเห็นและแก้ได้ service, route, plugin, consumer จะโผล่ในตารางของ tool เอง ผลที่ตามมามีทั้งดีและอันตราย ต้องจัดการทุกข้อ

อันตรายข้อที่หนึ่ง — ลบตัวเองออกจากบ้าน

ถ้าใครลบ route admin-api หรือ consumer ที่ถือ credential อยู่ → เข้า Admin API ไม่ได้อีกเลย และแก้กลับผ่าน Admin API ก็ไม่ได้เพราะมันหายไปแล้ว ต้องกู้ด้วย kubectl exec เข้าไปแก้ DB หรือ restart ด้วย declarative config

Admin path guard — ทำที่ M0

ตอน sync ให้ tool หาเส้นทางนี้เองแล้วมาร์คไว้

1. เอา connection.admin_url                    → host + path
2. หา route ที่ match host/path นั้น
3. ไล่ route → service → ถ้า service.url ชี้ไป 127.0.0.1 / localhost
   ที่ port ของ admin_listen                    → นี่คือ admin path
4. มาร์ค is_admin_path = true ให้:
   service ตัวนั้น · route ทุกตัวของมัน
   plugin บน service/route (basic-auth, acl, ip-restriction, rate-limiting, log)
   consumer ที่อยู่ในกลุ่ม ACL ที่ route นั้นอนุญาต
  • ลบ = บล็อกทั้งหมด ใน UI ต้องพิมพ์ชื่อ connection + ติ๊ก "ฉันรู้ว่านี่จะทำให้เข้าไม่ได้" · ใน MCP บล็อกสนิท ไม่มี override — agent ไม่มีทางลบเส้นทางเข้าได้
  • แก้ = เตือน พร้อมแสดงว่าเปลี่ยนอะไรและกระทบการเข้าถึงยังไง
  • entity เหล่านี้ติด tag สงวน kong-admin-path และ tool ปฏิเสธที่จะใส่ลงใน decK YAML ที่มัน render ไม่ว่ากรณีใด

อันตรายข้อที่สอง — deck gateway sync ลบเส้นทางเข้า

นี่คือความเสี่ยงที่รุนแรงที่สุดในโครงการนี้ deck gateway sync ลบทุกอย่างใน Kong ที่ไม่มีในไฟล์ ถ้า admin path ไม่ได้อยู่ในไฟล์และไม่ได้ถูกกันด้วย select_tags → merge ครั้งแรก = ไม่มีใครเข้า Admin API ของ env นั้นได้อีก รวมทั้ง CI ที่จะ sync รอบต่อไปด้วย

ต้องกันครบทั้งห้าชั้น ไม่ใช่เลือกชั้นเดียว: (1) อย่าให้ decK จัดการ admin path เลย ให้เกิดจาก Helm/bootstrap แทน (2) tool ไม่ render entity ที่ติด kong-admin-path (3) CI block PR ที่ deck diff แตะ entity ที่ติด tag นั้น (4) CI block PR ที่มี delete เกิน threshold (5) ซ้อมกับ uat ก่อนเสมอ

read-only credential — ทำแบบ Kong-native

rev ก่อนเสนอ nginx if block ซึ่งใช้ไม่ได้แล้วเพราะ proxy คือ Kong ท่าที่ตรงกับ Kong คือ สอง route + ACL plugin — config ล้วน ไม่มี custom code อ่านง่ายตอน CAB รีวิว

ทำไมต้องคนละ host

router ของ Kong เลือก route จาก host/path/method ก่อนจะรู้ว่าใครเป็นคนยิง ถ้าสอง route ใช้ host เดียวกัน DELETE จะไปเข้า route rw แทน — การจำกัด method จึงไม่แยกตามผู้ใช้ ต้องแยก host (หรือแยก path prefix + strip_path) แล้วให้ ACL กันไม่ให้ consumer ข้ามฝั่ง

พฤติกรรมที่ได้: DELETE https://kong-admin-ro.internal/services/x → ไม่มี route ไหน match → Kong ตอบ 404 {"message":"no Route matched with those values"} · tool ต้องรู้จัก signature นี้แล้วรายงานว่า "credential นี้เขียนไม่ได้" ไม่ใช่ "ไม่พบ entity"

ทางเลือกที่เบากว่า ถ้าไม่อยากมีสอง route — pre-function plugin บน admin route (ทีมเขียนอยู่แล้ว) ที่เช็ค method กับ prefix ของ consumer แล้ว kong.response.exit(405, …) เหลือ route เดียว กันออกจาก deck ง่ายกว่า แต่เป็น custom logic ที่ต้องอธิบายตอน CAB — แนะนำสอง route + ACL เป็นหลัก

error mapping — แยก "proxy ปฏิเสธ" ออกจาก "Admin API ตอบ"

พอมี Kong คั่นกลาง response อาจมาจากสองชั้นที่ต่างกันโดยสิ้นเชิง ถ้าไม่แยกจะ debug กันตาย

Kong::Client ต้อง map ทั้งหกกรณีเป็น exception คนละตัว และ UI ต้องแสดงข้อความคนละแบบ

ข้อดีที่ได้ฟรี — Kong log กลายเป็น audit ชั้นที่สอง

พอ Admin API วิ่งผ่าน Kong ทุก request ถูกบันทึกใน access log พร้อมชื่อ consumer แปะ file-log หรือ http-log บน admin route แล้วต่อเข้า log pipeline ที่ทีมมีอยู่ → ได้ audit trail ที่ อยู่นอกตัว tool และจับได้แม้แต่คนที่ curl ตรงเข้า admin host โดยไม่ผ่าน tool เลย

คำถาม "ใครแก้ prod นอก PR" เปลี่ยนจากการอนุมาน เป็นข้อเท็จจริงที่มีบันทึก — และเป็น drift source ที่สี่ ของฟรีอื่นบน admin route: ip-restriction จำกัด subnet, rate-limiting กัน agent ยิงถี่ตั้งแต่ชั้น gateway

Bootstrap chicken-and-egg

Kong เครื่องใหม่ยังไม่มี admin path → tool เชื่อมไม่ได้ ต้อง bootstrap ก่อนด้วย kong config db_import / Helm / declarative file งานนี้อยู่นอก tool — tool มีหน้าที่แค่ตรวจว่ามีแล้วหรือยัง แล้วบอกให้ชัดถ้ายังไม่มี

กับดักของ decK กับ credential

basic-auth เก็บ password แบบ hash · deck dump จึงได้ค่า hash ไม่ใช่ password จริง ถ้าเอา YAML ไป sync ที่อื่น password จะกลายเป็นสตริง hash นั้น — พังเงียบ → อย่าให้ decK จัดการ credential ของ consumer และ tool ต้องปฏิเสธที่จะ render basicauth_credentials ลง YAML

credential แต่ละคนอยู่ใน DB ในเครื่องตัวเอง ไม่เคยเข้า git — คนใหม่เข้าทีม pull repo แล้วเห็น connection ครบทุกตัว ใส่ credential ของตัวเอง แล้วพร้อมใช้

กฎความปลอดภัยของ connection

  • ปฏิเสธ http:// ยกเว้น localhost — ข้ามได้ด้วย flag ในไฟล์ config เท่านั้น ไม่ใช่ checkbox ใน UI
  • verify_ssl default true · internal CA ให้ใส่ ca_bundle_path ไม่ใช่ปิด verify
  • ห้าม log header Authorization เด็ดขาด — spec assert ว่า log ไม่มีสตริง Basic 
  • credential ไม่เคยถูกคืนจาก API ใด ๆ — คืนแค่ auth_username, has_credential, credential_kind, access_level
  • rate limit หน้า login (และแปะ rate-limiting บน admin route ด้วยยิ่งดี) · session timeout · re-auth ก่อน apply บน rank ≥ 2
  • ปุ่ม "ลืมทุก credential" ล้าง stored credential ทั้งหมดทันที

Azure Key Vault backend เป็นของ Enterprise แผนที่จะอ้าง AKV ตรงจาก Kong ใช้กับ CE ไม่ได้

ทาง ก — แนะนำ

Kong env vault + CSI driver

key: "{vault://env/cert-payments-key}" โดย CSI Secret Store Driver ป้อน env var เข้า pod ของ Kong จาก AKV

→ private key ไม่อยู่ทั้งใน git และ Kong DB

ทาง ข — fallback

decK env substitution

key: ${{ env "DECK_CERT_PAYMENTS_KEY" }} · CI ดึงจาก AKV แล้ว export ก่อน sync

→ git สะอาด แต่ plaintext ไปอยู่ใน Kong DB

กฎของ tool เหมือนกันทั้งสองทาง

  • redactor ทำงานก่อน data เขียนลง read-model — certificates.key, basicauth_credentials.password (แม้เป็น hash), keyauth_credentials.key, field ที่ schema ทำเครื่องหมาย encrypted/referenceable → "[REDACTED]"
  • MCP ไม่คืนค่าเหล่านี้ทุกกรณี ไม่มี flag ให้ปลด
  • แคชเฉพาะ metadata ของ cert: id, tags, SNIs, subject, issuer, not_before/not_after, fingerprint
  • digest คำนวณจาก data ที่ redact แล้ว — ไม่งั้น drift detection รั่วข้อมูลผ่านการเปรียบเทียบ

ผลพลอยได้: parse not_after เก็บไว้ → dashboard cert หมดอายุข้ามทุก connection ฟรี และได้ MCP tool kong_certs_expiring ต่อยอดงาน cert rotation ได้ตรง ๆ

API contract — filter, ordering, keyset

GET /api/v1/entities

  connection=prod  type=service   # บังคับทั้งคู่
  q=payment                       # trigram บน name + host + path
  tags=core,payment               # AND (ไม่จำกัด 5 tag)
  tags_any=beta,canary            # OR
  tags_none=deprecated            # NOT — Kong ทำไม่ได้
  created_after=  created_before=  updated_after=
  sort=-updated_at                # allowlist: name|created_at|updated_at
  limit=50   cursor=<opaque>
  fields=id,name,tags,updated_at  # สำคัญมากสำหรับ MCP — ลด token

{ "data": [ … ],
  "meta": { "has_more": true, "next_cursor": "eyJrIjpb…",
             "connection": "prod", "credential_mode": "stored",
             "access_level": "ro", "credential_kind": "shared",
             "stale_seconds": 47, "desired_state": "git@…#a3f19c2" } }

keyset ที่ต้องทำถูกตั้งแต่ต้น

  • ทุก sort ต้องมี tiebreaker: ORDER BY kong_updated_at DESC, id DESC — ไม่มี = แถวซ้ำหรือหายแบบเงียบ
  • index ต้องตรงกับ sort key เป๊ะ → จำกัด sort เป็น allowlist ห้ามต่อ input ผู้ใช้เข้า ORDER BY
  • cursor = base64url {"k":[…,<id>],"s":"-updated_at","f":"<hash ของ filter>"} + HMAC · f ทำให้เปลี่ยนฟิลเตอร์กลางทางแล้ว cursor เสียทันที
  • ไม่มี total ฟรี — UI ใช้ปุ่ม "โหลดเพิ่ม" ไม่ใช่เลขหน้า
  • session mode → meta.partial: true + แบนเนอร์ · access_level: ro → UI ซ่อนปุ่มเขียนตั้งแต่แรก ไม่ใช่ให้กดแล้วค่อย error

Drift สี่ทาง

เทียบอะไรแปลว่าทำยังไง
cache ≠ Kongcache เก่าreconcile รอบถัดไปแก้เอง
Kong ≠ gitมีคนแก้ Kong ตรง ข้าม PRแจ้งเตือน
git ≠ Kong หลัง mergeCI sync พังหรือยังไม่รันเช็ค pipeline
Kong access log มี write
ที่ไม่มี change_plan		มีคนยิง Admin API ตรง โดยไม่ผ่าน tool เลยระบุตัวได้จาก consumer ใน log

คู่ที่สี่มาจากข้อ 01 — เป็นชั้นเดียวที่จับคนที่ไม่ใช้ tool เลยได้ · Sync สามชั้น: write-through หลัง mutate (direct) · full reconcile ต่อ connection ทุก 2–5 นาทีแบบ jitter และ fail closed (sync ไม่ครบ = ไม่ soft-delete อะไรเลย) · digest diff → drift event

หน้าบ้าน

Rails 8 + Hotwire (Turbo Frames/Streams) + Stimulus + ViewComponent + Tailwind — codebase เดียว ไม่มี build pipeline แยก ไม่มี CORS งานหลักคือ "ตาราง + ฟิลเตอร์ + ฟอร์ม" ซึ่ง Turbo Frame แข็งที่สุด และ keyset เข้ากับ Turbo Stream append พอดี

หน้าจอ

  • Connections — list / add / edit / test / delete พร้อมสถานะ, ป้ายสี, access_level, credential_kind
  • Login — basic auth + ช่อง operator (ถ้าเป็น credential ร่วม) + error ที่แยกตามตารางข้อ 01
  • Switcher ใน header — prod แถบแดงเต็ม + ป้าย "read-only" + ป้าย "credential ร่วม — บันทึกในนาม X"
  • ตาราง entity — แถวที่ is_admin_path มีไอคอนกุญแจและปุ่มลบถูกปิด
  • รายละเอียด: Overview / ลูก ๆ / Plugins / Raw JSON / History
  • Review diff · Audit log · drift (สี่ทาง) · cert หมดอายุ · PR ค้าง · หน้า PAT

ฟอร์ม plugin สร้างจาก schema

ดึง GET /schemas/plugins/:name มา render อัตโนมัติ แล้วเขียน custom UI ทับเฉพาะที่ใช้บ่อย (rate-limiting, key-auth, pre/post-function ของทีม) รองรับ custom plugin ได้ฟรี

plugin บน admin route (basic-auth, acl, ip-restriction) แสดงเป็น read-only

ที่ยังต้องรู้

ก่อน M0 — สามข้อนี้ block

  1. admin route ตอนนี้แยก rw/ro แล้วหรือยัง ถ้ายัง — สร้างเพิ่มได้ไหม (สอง host หรือสอง path) หรือจะใช้ท่า pre-function แทน
  2. admin path ตอนนี้เกิดจากอะไร — Helm values / declarative bootstrap / คนสร้างมือ → กำหนดว่าจะกันออกจาก deck ยังไง
  3. consumer ที่ใช้ร่วมกันมีตัวไหนบ้าง → เอาไปติด tag shared-credential ครั้งเดียว

ก่อน M2

  1. Git host อะไร — GitHub / GitLab / Azure DevOps / Bitbucket
  2. config repo มีอยู่แล้วหรือยัง และ prod จัดการด้วย deck 100% หรือบางส่วน
  3. decK เวอร์ชันไหน — deck sync vs deck gateway sync

ก่อน M5

  1. ตอนนี้ private key ของ cert อยู่ที่ไหน — inline ใน Kong, env var, หรือ AKV แล้ว

อ้างอิงพฤติกรรมของ Kong Gateway 3.x และ decK — ตรวจกับเวอร์ชันที่ใช้จริงก่อนล็อก contract · rev 4, 28 ส.ค. 2026
